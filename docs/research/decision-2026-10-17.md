# Research decision report — 2026-10-17 (after Phase 1 of the charter)

*Inputs: `docs/research/CHARTER.md` (gates set before the analysis), `docs/experiments/2026-10-17-kv-reuse-oracle-study.md`
(Phase 1, Steps 1–4; trace simulation on the Mooncake traces at 200 GiB), and the campaigns listed in the charter's
evidence table. No system code was written; no hardware experiment was run.*

## Gate results
- **Gate 1 (future information has value): PASS, by a wide margin.** An oracle that knows every future access serves
  80 / 94 / 70% of reuses (conversation / tool agent / synthetic) where the best capacity-matched baseline serves
  17 / 65 / 34%; recomputed tokens fall 26 / 27 / 43%; bytes written to host memory fall 82 / 83 / 70%. The gain comes
  almost entirely from not storing the 58–79% of blocks that are never used again: at 200 GiB and ~52 new blocks/s a
  cache that stores everything turns over in about a minute, and the median first reuse comes after ~150 s. Future
  information is worth more than 5× the capacity (the oracle at 200 GiB beats LRU at 1 TiB), and knowing the next use
  within 300 s is enough (94% of the oracle).
- **Gate 2 (the information is predictable online): FAIL for both real workloads.** Every creation-time or session-level
  feature in the traces (block position, prompt and answer length, continuation depth, turns so far, time since the
  previous turn, new blocks per request) moves the reuse probability within 10–35% of a 22–24% base rate; the strong
  signals (a past reuse → 42–98%; 300 s idle → ≤ 4% alive) appear only after a residence the 200 GiB cache does not
  grant. Simple online rules fitted on the first half of a trace — segmented LRU, reactive promotion, admission filters,
  frequency-first eviction — recover at most 6% of the oracle's gain on the second half (criterion: 50%). The synthetic
  trace is predictable from request features, but it is synthetic.

Per the charter, Phase 2 (joint value-and-interference policy) does not start on this basis, and no predictor is built.

## The seven questions
1. **Is the value of oracle future information worth researching?** The value is real and large, but the research
   question it raises is not "how to predict reuse from block features" (that fails) but "where can a serving system get
   the lifetime of a block from" — a session-level signal that a conversation will continue within minutes (an open
   client connection, a client-side end-of-session, an application hint). That is an interface question, testable
   offline first (below), and it is worth one focused study because the payoff is 3–5× effective capacity and a 70–80%
   cut in host writes — the largest interference lever found in this project.
2. **How predictable are the existing traces?** For conversation and tool agent: not usefully (lift ≤ 1.5× at creation;
   ≤ 6% of the ceiling online). History and idleness are strong but late. The traces carry no session ids; reconstructed
   conversations show that continued conversations are *less* likely to continue again, so turn-counting does not help.
3. **Is reuse-aware admission sufficient?** Admission is where the value is (bypassing dead blocks is 80% of the oracle's
   gain), but it needs a signal we do not have. Without one, admission by a static DRAM share plus LRU is within ~1–3
   points of every online alternative, and a segmented LRU (protect on first hit) is the only cheap, safe improvement.
4. **Are migration and prefetch necessary?** For hit rate, no: the oracle with ideal tier assignment equals the oracle
   without it, and reactive migration's +3 points equal a logical segmented LRU that moves nothing. Migration keeps a
   role only on the cost side (where in DRAM/CXL a block is written and when) and for CPU readers of DRAM. Prefetch from a
   lower tier has the same information problem as admission and is not justified now.
5. **How do the DRAM/CXL interference results fit a unified manager?** As its write scheduler: CXL-first by default; a DRAM
   write budget bounded by the neighbours' SLO (the probe-based guard finds none beside busy neighbours; 6–8 GB/s is safe;
   a budget that follows the neighbour's phases halves the 70B backlog); CXL write capacity (~46 GB/s) and CXL read
   protection shared across writers (checkpoint + KV). These mechanisms do not need a value signal to be useful — they
   decide *where and when* bytes are written. A value signal would multiply their effect: the oracle's bypass removes
   70–80% of the KV writes, which is more than any budget can buy.
6. **The one mechanism most worth implementing next.** Not a predictor. Two candidates, in order: (a) *offline first*: a
   session-hint oracle — an oracle that knows only whether a conversation has another turn (not which blocks, not when)
   — to measure how much of the block-level ceiling a perfect application hint would capture; (b) *in the system*: the
   lifetime-hint admission path (bypass or short-TTL for blocks the application marks as end-of-session) on top of the
   existing exclusive two-tier placement, if (a) is positive. Independently of Gate 2, the SLO-safe DRAM write budget
   estimator remains the one RQ3 mechanism whose necessity the data already show; it is required by the manager whatever
   the value side yields.
7. **Directions to drop.** ML reuse predictors on block or request features (no signal to learn from in these traces);
   promotion/demotion engines for hit rate; a global-LRU unification as a contribution (no gain); predictive prefetch;
   further bucket-depth or static-split tuning; capacity sweeps as a result (the ceiling is known).

## Minimal system design (sketch; `docs/DESIGN.md` §11)
Keep: the `cxlpath` store and CXL-first write path; exclusive tiers with per-tier LRU and a DRAM admission share (the
static split) as the default placement; a segmented (protect-on-first-hit) retention order, logical, no data movement.
Add: a block-lifetime interface (application hints at creation: no-reuse / session-continues / unknown) consumed by
admission (bypass, short TTL, or store) — the only path through which the Gate-1 value can enter the system; the write
scheduler from RQ3 (DRAM write budget under the SLO, CXL capacity accounting, cross-writer arbitration, CXL read
protection) deciding when DRAM is written. Leave out: promotion/demotion for hits, prefetch, ML prediction, a general
memory manager. The design is a sketch; nothing is implemented.

## Next experiments, in order
1. **Session-hint oracle (offline, trace simulation, 1–2 days).** Oracle that stores a request's new blocks only if the
   conversation has another turn (perfect hint), and variants: hint known only at the end of the request; hint with
   a time bound ("continues within T"); hint with error rates (10–30% false positives/negatives). Gate: ≥ 50% of the
   block-level oracle gain with a perfect hint, degrading gracefully with errors. If it fails, the lifetime interface is
   dropped and the KV side of the paper rests on placement and write scheduling alone.
2. **Hint-driven admission in emulation (kvemu2 with trace-derived hints, no node time beyond a day).** Hits, writes and
   neighbour slowdown with perfect and noisy hints beside the Adam step and the reader, against the static split.
3. **Online safe-budget estimation (RQ3; hardware).** The estimator vs the oracle budget and the static splits across the
   four neighbours and on/off phases (the charter's Gate 4 metrics), unchanged from the 2026-10-13 proposal.

## Not supported, and therefore not claimed
H1's online half (A2) is not supported by the traces; H2 (joint value × cost) could not be tested without a value signal
and stays a hypothesis. The paper cannot claim prediction-aware management until experiment 1 above passes.


## Update 2026-10-17 (evening) — session-level hint study (`docs/experiments/2026-10-17-kv-session-hint-study.md`)
The last exploratory experiment on reuse predictability, per the user's brief. Reuse is within-session (89–100%) and the
next turn re-reads ~80% of a turn's blocks, so a session signal targets the right blocks. A *perfect* "session continues"
hint (oracle) recovers 40–54% of the block oracle's gain (0.51 / 0.77 / 0.49 reuse-hit share vs 0.17 / 0.65 / 0.34; writes
−45–66% with admission; recompute −11–17%), and 74 / 51 / 41% with a 300 s bound; the gain is retention (eviction-only
= both). What a real system can obtain: online session state (recency, idle time) adds nothing over LRU; a termination
event 60 s late adds nothing (LRU has evicted the blocks by then at 200 GiB); a termination event within ~10 s adds
28–41% of the ceiling — realistic for agent frameworks (turns chain within seconds, the orchestrator knows when a task
ends), not for chat clients. False positives (keeping dead sessions) cost a fifth of the benefit at 10% and half at 30%;
false negatives are cheap; 30% missing hints halve it.

**Gate 2 update:** FAIL for chat (only oracle hints clear 50%); borderline for agent workloads (28–41% with a prompt
task-end event — an application interface, not a predictor). **Go / No-Go: NO-GO for a prediction-aware unified
manager; Case B for chat, weak Case A for agents.** Stop the reuse-prediction direction as a research contribution. Keep
an explicit, immediate "lifetime release" event (task end / end of session) as an optional interface of the manager —
a mechanism that costs nothing and helps agent workloads — and return to the charter's problem with the focus on
capacity-aware placement, interference-aware admission, data-lifecycle management (explicit release, TTL) and
cross-application coordination. Nothing of this is implemented; the next step is the design discussion the user asked for.


## Update 2026-10-17 (night) — RQ1-B: application-level reuse signals (`docs/experiments/2026-10-17-rq1b-application-reuse-signals.md`)
Source inspection (vLLM 0.31, LMCache 0.5.5, OpenAI Agents SDK, LangGraph) + real-run lead times + trace replay. What
applications know early: queued requests' exact block hashes (vLLM computes them at arrival; LMCache can look them up at

an oracle for chat. Chat clients have no early signal. Writes are avoided by an end event only if the store is deferred
(LMCache lazy offload). **Gate 2: FAIL for chat, PARTIAL for agents (41–48% vs the 50% criterion).** Recommended single
scheme: the agent-runtime lifecycle channel (one per-request field via `kv_transfer_params`/`cache_salt` → LMCache
`request_finished`: evict-first + drop pending stores on end, bounded pin on continue), verified by one small real agent
run with logged loop decisions before anything is built. The queued-request pin is not worth a project. No predictor.


## Update 2026-10-17 (late) — RQ1-B real agent runtime validation (`docs/experiments/2026-10-17-rq1b-agent-runtime-validation.md`)
Real runs on c28's 4060 Ti: OpenAI Agents SDK 0.24 (unmodified loop, logging hooks only) → Qwen2.5-3B-Instruct-AWQ on
vLLM 0.31 + LMCache 0.5.5 (DRAM L1 1 / 4 GB, GPU cache capped), 400 tasks × 3 runs (8 / 16 agents), LMCache's own event
bus mirrored to JSONL (lookup chunk hashes, stores, writes, evictions, end_session), replay of the real trace with the
real events. **Verified:** the runtime knows continue / end at `on_llm_end` / `on_agent_end` with no delay; on continue
100% of the context is re-read 1.3 s later (tool time) and 87% of the next call's chunks already exist; on end 84–85% of
the task's private chunks are dead (the rest: identical later prompts) and 92% of its shared chunks (system prompt) are
live, so the end event needs the task id and a live-reference count; the end event comes 0.4 s **after** the last KV
write; at L1 ≥ the live working set LRU already serves 96.5–98.6% of the reuses (reuse interval 1.3 s vs turnover
10–100 s). **Simulated on the real trace:** events recover ≥ 50% of the oracle's gain over LRU only when the cache is
smaller than the live working set (16 agents, 0.23–0.30 GB: end 39–55%, end + continue 59–66%); ≤ 4% at or above it;
deferred stores dropped on end would cut writes 49% (LMCache's lazy offload crashed the engine, so not measured); under
LRU 74–86% of the cache-time holds dead blocks. **Gate 2 for agents: PARTIAL** — information PASS (timely, exact);
hit-rate value FAIL at normal capacity, PASS only under capacity pressure; write value simulated only. The previous
round's 41% (reconstructed events, Mooncake agent trace, 200 GiB) is neither confirmed nor contradicted: that trace's
turn gaps (p90 150 s) are not this loop's (1.3 s). **Recommendation:** do not build the next stage on hit-rate prediction
for agents; keep the lifecycle event as a cheap release + deferred-store interface whose value is write avoidance and
capacity release, to be evaluated with the write scheduler (RQ3). Nothing implemented; no cxlpathd change.


## Update 2026-10-17 (final RQ1-B round) — reuse horizon vs cache residence (`docs/experiments/2026-10-17-rq1b-reuse-horizon.md`)
Three real quantities decide whether a lifecycle hint can help: the reuse horizon H (previous → next use of a task's own
chunks), the LRU residence T_res = C / P, and the live working set W_live. Evidence: a PUBLIC trace with real timestamps
(Exgentic/agent-llm-traces, 1,781 sessions, 6 benchmarks, 5 harnesses: horizons 6–11 s p50 / 20–36 s p90, prompts
20k–60k tokens); REAL runs with tools that really execute (pandas / pytest / Python, 2.5–15 s; continue lead 2.9–3.3 s
p50, 10–14 s p90) at 8 / 16 agents with and without REAL background churn (the Mooncake conversation trace on the same
server); replays of six real traces over 9 capacities × 4 churn levels (144 settings) with LRU, SLRU, session TTL,
continue-only / end-only / both and the oracle. **Result:** LRU keeps a context whenever T_res > ~2 H, which every
sensibly sized cache does (short tools: 96–99%; real tools at 1 GB: 97–99%; with 3 GB/s-class real churn: 98%). The
continue signal recovers ≥ 50% of the oracle's gain only in the band W_live ≲ C ≲ P · H (77–93% with synthetic churn,
90–91% with real steady churn, +3 … +7 points) and 51–70% when the cache is below the live set (+7 … +9 points of a
capacity-bound oracle); the median over all settings is 0%. The gain is from protecting live data: continue-only equals
end+continue, end-only ≤ 37% and net negative outside the band (15% false positives from repeated prompts). Under bursty
churn SLRU (50–60%) beats the signal (10–20%). ESTIMATE from the public traces: a 200 GiB tier serving ≤ 64 agents of an
8B model sits at H / T_res = 0.01–0.25 (LRU regime); the band needs a cache within a few horizons of its churn (e.g. ~20
GiB under 3 GB/s of foreign KV) or ≥ ~256 agents (capacity-bound). **Gate 2: PARTIAL** — met only inside a constructed
band, not in the no-pressure and moderate-pressure scenarios; threshold unchanged. **Decision:** RQ1 is answered: future
reuse information is valuable (Gate 1) and the agent lifecycle is the only online source, but its hit-rate utility is
confined to a narrow regime; the joint benefit analysis must not be built on reuse prediction for agents. The lifecycle
event's write-side and occupancy value (previous round, simulated) is untouched by this round. No RQ2/RQ3 work started.


## Update 2026-10-18 — RQ1 miss-cost feasibility (`docs/experiments/2026-10-18-rq1-misscost-feasibility.md`)
Can a realistically obtainable miss-cost signal complement reuse information? **Measured** (3B-AWQ on the 4060 Ti,
LMCache L1 in DRAM and on the CXL devdax): recompute 0.134 ms/token rising 7% per 1k tokens of position; load from
either host tier below the floor (≤ 1/15 of recompute, ≤ 1/50 under contention); a hole at f·L costs exactly a prefix
of f·L (prefix-dependent, request-level miss cost; blocks behind a hole are worthless). **Source:** vLLM and LMCache
already evict tail-first, so the one structural heterogeneity is already exploited; every cost feature is available
online. **Replays** (prefix-aware scoring, LMCache order, measured cost model; agent traces and Mooncake at 100–400
GiB): cost-aware retention recovers −50 … +2% of the oracle's TTFT gain, 0% on Mooncake; SLRU + cost = SLRU; continue +
cost ≤ continue; a pure cost ranking yields 0 hits; ±50% cost error changes nothing. **Answers:** Q1 heterogeneity only
structural (already used); Q2 available online; Q3 no benefit; Q4 no complement; Q5 useful as an accounting rule
(keep chains whole; DRAM vs CXL placement does not change KV miss cost at this scale) but not as information. **Gate 2
unchanged (PARTIAL).** RQ1 closed: the value input to RQ2 is recency / frequency, chain structure and agent lifecycle
events; any joint benefit must come from the movement / interference side, which changes the premise of H2's value
half. No RQ2/RQ3 work started.


## Update 2026-10-20 — RQ1-B historical reuse-pattern learning and online prediction (`docs/experiments/2026-10-18-rq1b-history-learning.md`)
Strictly chronological study on the Mooncake traces, the synthetic trace and the real agent traces. **Characterization:**
the public traces carry no session / tenant / app ids; the conversation trace has one root (one system prompt) and no
large sub-groups, the tool-agent trace 4 roots with stable 2% vs 24% new-block reuse; reuse is concentrated (top 0.1%
of blocks carry 15% / 63% of reuses); popularity does not persist between 5-min windows (9–18% of a window's top-100
stay); LRU at 200 GiB loses 82% / 36% of reuses, half of them blocks with reuse history, evicted 39 s after the last
use and needed 108 s later. **Prediction (prequential, 5 time segments):** new blocks unpredictable (AP 0.045 vs base
0.037 at 60 s; ≤ 1.3× lift at 300 s); observed blocks highly predictable from their own history (AP 0.75 vs 0.20,
0.99 vs 0.65; stable); next-use time within 2× for 59–73%. **Cache utility (prefix-aware replay, LMCache order):**
retention-only learning = LRU (0–3% of the oracle's gain; SLRU 4–5%); learned admission (class hit-rate feedback,
bypass below 0.15) is the first online method beating SLRU on both real traces: 0.178 → 0.274 (conversation) and
0.648 → 0.691 (tool agent) usable-prefix hit share at 200 GiB, 14–16% of the oracle's gain, +4.7–5.1k net hits, writes
−66 … −78%; the rule it learns is "do not store deep blocks of continuing conversations"; negative on the synthetic
trace; threshold hand-set (0.15), not tuned per trace. No prefetch opportunity without a lower copy. **Gate 2 stays
PARTIAL.** New for RQ2: a self-labelling admission filter with near-oracle write savings; still missing: any signal for
the reused minority of fresh requests, and any persistence of popularity.

## Update 2026-10-20 (late) — RQ1-B admission study: mechanism, static vs learned, generalization, oracle gap (`docs/experiments/2026-10-20-rq1b-admission-study.md`)
**Question:** what the learned admission filter of the previous update actually learns, whether online learning beats
static rules, whether its feedback is correct and leak-free, how it generalizes, and what the remaining oracle gap is.
**Correction first:** the previous round's class was effectively (root, position) because of a depth bug; fixed and
every configuration rerun — the corrected class policy reaches 22% / 25% of the oracle's gain at 210 GiB (was 14–16%).
**Mechanism (per-access accounting):** the filter refuses 63–70% of LRU's admissions, 75–78% of them never read again;
host-cache writes −69 … −77%; because the LRU residence is capacity / admission rate, admitted blocks stay 123–156 s
instead of 42 s, i.e. one reuse horizon (next use ~105 s after the eviction LRU would have made); the gained hits are
re-reads of blocks with ≥ 2 past uses, the lost ones the second touch of blocks refused at their first — the signature
of **second-touch admission**. Retention ranking cannot do this because it cannot change the residence.
**Static vs learned (three kinds kept apart):** request-structure rules (position / prefix / k-th new block) 2–20% and
fragile (position rule −42 … −217% on the tool-agent trace, −24 … −70% at 839 GiB); the parameter-free second-touch
rule (admit only hashes looked up before; ghost set) **26% / 29% at 210 GiB and 22% / 24% at 419 GiB with the fewest
writes (−75 … −77%)**, +5 … +16% on the synthetic trace; the learned class policy 22% / 25% and 16% / 16%, but 15–20% at
52–105 GiB where the rule gets 5–14% (it refuses re-seen blocks whose class cannot survive a 30-s residence), and
≥ −4% where the capacity covers the horizon (839 GiB; real agent traces at 32–48 chunks) where the rule is −9 … −303%.
Interleaved mix: learned 19%, second touch 12%, request rules 4%; phase change: second touch 31%, learned online 26%,
frozen 0%.
**Feedback audit:** every input is a lookup / hit / eviction of a hash (all on LMCache's event bus); labels arrive
114–120 s after admission; censoring of refused classes is real but the 20-min decay handles it — ε-exploration and
bypass feedback change the result by −1 … −3 points and add 0.5–2.4 TB of writes; threshold 0.10–0.25 gives 19–25%
(class policy); nothing chosen on the scored half, no future information.
**Oracle gap:** one identifiable category — 17.9% / 17.1% of new blocks that the oracle admits and the filter refuses,
100% reused (p50 102–111 s), 97–98% in fresh requests, indistinguishable from the 73–74% dead blocks of the same
classes (lift ≤ 1.25 on any request feature) — plus 7.6% wasted admissions near the threshold. Both "both-refuse"
classes are 99% dead; nothing is left to learn at the block level.
**What changes in the assessment:** the previous update's "learned admission is the first online method beating SLRU"
stands, but the method is not the learning: it is admit-on-second-touch, a classical ghost-cache rule, which does
better at the capacities where admission matters most. The learned class rates are worth keeping only as the capacity-
awareness layer (when even second-touch blocks will not survive, and when filtering should stop). The useful-admission
rate goes 31–33% (LRU) → 42% (learned) → 48–51% (second touch); the oracle is 100%.
**Decision:** Gate 2 stays **PARTIAL** (22–29% at 210 GiB; threshold ≥ 50% unchanged). RQ1 remains closed. The value
input to RQ2 is: recency for retention; a history-based admission filter (second touch + class rates + the online
residence estimate) for admission and host writes; the agent lifecycle events for fresh-request reuse of agents.
**Not claimed:** any measured DRAM/CXL interference reduction (the write reduction is a replay number); any real-system
speedup; a bounded ghost set (the replay's seen-hash set is unbounded; 366k entries for an hour of trace).

## Update 2026-10-21 — RQ1-B practical and adaptive reuse-aware admission (`docs/experiments/2026-10-21-rq1b-adaptive-admission.md`)
**Question:** can second-touch admission be deployed with bounded history, can admission adapt online to the relation
between reuse horizon and cache residence, does history learning add anything over strong existing online policies,
is the online feedback correct, and what of the remaining oracle gap is learnable?
**Method:** a new simulator (`scripts/kv_admission_sim.py`) with the 2026-10-20 semantics, validated to the block
(LRU / SLRU / second touch / learned class / oracle identical); 2Q, ARC, TinyLFU (adapted, window-less), W-TinyLFU
implemented as published; ghost history exact-bounded / TTL / Bloom; class tables with policy-independent
"looked-up-again-within-w" labels; parameter selection on the first half only; walk-forward fifths, cold start,
freezing; GPU front cache; LMCache source inspection for observability.
**Findings.** (1) *Bounded history:* 64k ghost entries (2 MB) = unbounded; 16k (0.5 MB, one reuse horizon of new
hashes at 52 / s) or a 2 × 8 KB double-buffered Bloom filter match or beat it at 52–210 GiB (0.391 vs 0.339 usable
share at 210 GiB) because forgetting after ~300 s is a gap filter; < 8k entries collapse; Bloom false positives are
first-touch admissions and cost hits. (2) *Adaptation:* the online residence estimate (mean eviction age) is the one
quantity that matters; the rule "admit a re-seen block only if its last gap fits the residence" (`2nd_int`, no
parameter) is the best or within 2–3 points of the best policy at 52–419 GiB on both real traces — 21 / 29 / 33 / 23%
and 21 / 26 / 32 / 21% of the oracle's usable-hit gain at 52 / 105 / 210 / 419 GiB with 1.8–2.8 TB written (LRU
16–19 TB), 27 / 32% on the constructed mixes, identical on the selection and the test half. (3) *Existing methods:*
TinyLFU (adapted) is the strongest — 21–27% at 105–210 GiB with the fewest writes — but keeps filtering when capacity
is plentiful (4 / 1% at 419 GiB, −55 / −70% at 839 GiB) and is negative on the synthetic trace; 2Q / ARC / W-TinyLFU
write everything and gain ≤ 7% at ≤ 419 GiB; ARC is right at 839 GiB (+13 / +18%). History adds 6–20 points over
TinyLFU at every capacity ≤ 419 GiB, all from the last-touch time compared with the residence. (4) *Feedback:*
class tables with re-lookup labels are identical under LRU, second touch and the oracle (no censoring, no selection
bias, no exploration needed); the 2026-10-20 hit-before-eviction label differs by 0.04–0.43 and collapses the policy
when used; frozen statistics = LRU; cold start recovers in 3–4 fifths. (5) *Class tables do not beat the one rule:*
no more hits for 2–3× the writes at ≤ 419 GiB; fewer classes are better; the configuration selected on the first half
(touch-count classes, fixed threshold 0.5) scored 14–31% on the test half and −37 / −51% at 839 GiB; the replanned
variants are the only filters not strongly negative at 839 GiB (−6 … +10%). (6) *Oracle gap* at 210–419 GiB: 62–80%
the first-touch cost (no first-touch class above a 21% chance of a re-lookup within the residence — information the
host does not have), 12–30% blocks admitted but evicted before a long-gap reuse (dead-block pollution: 49–52% of
admitted blocks are never reused and nothing in their past separates them), ≤ 20% long-gap re-seen blocks refused.
(7) *Semantics:* with a 34–69 GiB GPU prefix cache in front, the served usable share is unchanged (±0.002) while the
host's own hits fall (LRU 0.178 → 0.06): the policies' gains are entirely in the long-gap range; LMCache's store path
computes every chunk hash (`token_database.process_tokens`), so a bypassed block's re-appearance is observable.
**Decision:** Gate 2 stays **PARTIAL** (32–33% at 210 GiB, 21–29% at 52–105 / 419 GiB). RQ1 remains closed. The
value input to RQ2 is now concrete and deployable: per block at the host-write boundary, "looked up before" (bounded
ghost or Bloom), the gap since that lookup, and the cache's residence estimate; the admission decision `2nd_int`, or
P̂(re-lookup within residence | touch count, gap) with policy-independent values; plus the agent lifecycle events for
fresh-request reuse; plus a regime switch (residence ≥ gap p90 → stop filtering, ARC / SLRU). Not learnable from
history: first-touch reuse (16–21% base rate, no separating feature) and the dead half of second-touch admissions.
**Not claimed:** measured interference reduction (write volumes are replay numbers); real-system speedup; a
deployment of the Bloom ghost; the agent-trace τ / window settings (scaled by hand, not selected).

## Update 2026-10-21 (second round) — RQ1-B robust online reuse information and adaptive admission (`docs/experiments/2026-10-21-rq1b-robust-admission.md`; consolidation `docs/research/rq1-consolidation-2026-10-21.md`)
**Question:** can the gap rule's inputs be made reliable and adaptive — when to stop refusing first touches, how to
estimate the residence stably, with bounded metadata and correct prefix semantics — and what is the consolidated RQ1
answer and the value-information interface for RQ2?
**Findings.** (1) *Regime adaptation:* `2nd_int` loses at large capacity because it never admits first touches and
the first reuses it loses (11.5–12.0k at 839 GiB) outnumber the long-gap blocks it protects (9.0–9.6k); the rule
"normal admission when C / (λ_first + λ_re-seen) ≥ the online median re-lookup gap of first-touch blocks" (30-s
hysteresis; inputs: lookups / stores / evictions / time) stays in the filter regime at 52–419 GiB (no switch in the
scored half, 21–33%) and switches at 839 GiB on both traces (0% with an LRU structure, +12 / +17% with SLRU, vs
−10 / −19%); selected on the first half, confirmed on the test half; the re-seen gap median (15 s on the tool-agent
trace: immediate re-touches) and a predicted-hits model are wrong criteria (0% at 105–419 GiB on the tool-agent
trace); hysteresis does not matter; after a load step at 839 GiB the rule re-enters filtering 14 min later or not
within the hour (conservative); not usable on 100-s agent traces. With the SLRU structure the policy is above
`2nd_int` at every capacity (24–35% at 52–210 GiB) and never negative under the dynamic scenarios. (2) *Residence
estimation:* the EWMA of dead-eviction ages and the LRU-tail age are unbiased (within 2× for 100% of admissions at
≥ 210 GiB, 86–90% at 52 GiB); the previous default (all evictions) over-estimates 1.3×, capacity / write rate 1.4×;
the gap rule's hits do not depend on the estimator (33 / 32% at 210 GiB with all seven), writes differ by 0.3 TB;
the admission–residence loop is negative with a unique fixed point and settles within 0.7–1.9 min after a doubled
write stream, no oscillation (lag-1 autocorrelation 0.00–0.02); only 3–6% of the rule's admissions are lost to an
over-estimate, its refusals' errors come from the last gap (2×-accurate), not the estimate. (3) *Bounded metadata and
semantics:* 16–64k-entry ghost (0.5–2 MB) or 2 × 8 KB Bloom; under +50 never-reused blocks / s the gap rule keeps
0.31–0.33 / 0.71 of the usable share (0.38 / 0.74 without), the Bloom filter degrades more (its reset is counted in
inserts); the prefix-semantics audit holds on all 230 policy-capacity runs; LMCache exposes every needed event
(`cache_engine.lookup`, `token_database.process_tokens` on the store path, `StorageBackendListener.on_evict`,
`cache_policy.update_on_hit`); not observable: GPU-served lookups at lookup time (seen at store time) and the request's
future. (4) *Baselines across regimes:* small / moderate caches — the gap rule (with or without the switch) is the best
or within 3 points of the best; TinyLFU 11–27% at ≤ 210 GiB then −7 … −70%; large caches — only non-refusing policies
(SLRU / ARC, or the switched rule with the SLRU structure) are positive. (5) *Mechanism:* at 210 GiB the rule avoids
12.5k misses (blocks with ≥ 2 past uses, long gaps) and introduces 1.7–2.0k (second touches of refused first touches);
at 839 GiB 9.0–9.6k vs 11.5–12.0k; the switch reproduces LRU / SLRU exactly there and costs nothing below.
**Decision:** Gate 2 stays **PARTIAL** (32–35% at 210 GiB; error cost 13–16% of the gain, the second Gate-2 criterion
is met). RQ1 is consolidated (`rq1-consolidation-2026-10-21.md`): the information that is reliable online is "seen
before", the last gap, the touch count, the cache's residence (dead-eviction EWMA or LRU-tail age) and, for agents, the
lifecycle hint; the first-touch reuse and the dead half of second-touch admissions are not learnable by the host. The
value-information interface for RQ2 is written there; the deployable admission signal is the gap rule with the
first-touch-horizon regime switch on an SLRU structure.
**Not claimed:** measured interference reduction (replay write volumes); real-system speedup; a production
implementation (the LMCache event paths were inspected, not modified); the agent-timescale regime switch.

## Update 2026-10-21 (Phase 3) — joint benefit analysis: reuse value × DRAM/CXL movement cost (`docs/experiments/2026-10-21-joint-benefit-analysis.md`)
**Question (Gate 3's premise, tested offline):** with the same online reuse information (RQ1: seen-before, last gap,
residence, class rate, regime), the same 200 GiB (64 DRAM + 136 CXL, single copy), the same measured resources (CXL
path 46 GB/s; DRAM write budget under the Adam / reader p99 curves of 2026-10-12; checkpoint co-writer on the same
path) and the same selection rule (first half) — does a joint value-and-cost policy beat the independent combination
of reuse-aware admission and budget-gated placement?
**Findings.** (1) *Pressure after RQ1 (Task A):* the admission removes 88–91% of the write volume and all of its tail
at every scale (8B / 70B × 1 / 4 / 8×): peaks ≤ 25 GB/s against a 46 GB/s path, DRAM 0.2–2.1 GB/s against a 6–8 GB/s
safe budget, CXL backlog ≤ 1 GB, estimated Adam p99 0.1–1.9%; without it the same stream saturates the path 62% of
the time at 70B 4× (backlog 58 GB) and continuously at 70B 8× (10.5 TB) and breaks the SLO from 8B 8× on (+10 … +36%).
The write-interference problem measured in 2026-10-10/12 is a property of admit-all caching. (2) *Coupling (Task B):*
value does not change placement (reads are tier-independent; online value placement ±0.007 vs hash; the oracle's own
placement ≤ +3.4 points at 70B 8×), cost never changes admission (0 drops, 0 budget refusals, 0 regime vetoes in every
real-trace run), value does not make migration pay (−0.006 … −0.018). (3) *Baselines (Task D, 24 configurations):*
joint − independent = −0.005 … +0.007 usable hit share (mean +0.0004); reuse-aware only (RQ1 admission + static split,
no cost module) within 0.007 of both; cost-aware only = the split's hits with SLO safety; the value oracle under the
same costs loses ≤ 0.02 to the unconstrained oracle. (4) *Regimes (Task E):* low pressure, DRAM interference, CXL
saturation (none after filtering), half capacity (joint −0.3 … −0.9), checkpoints at 60 / 15 s (joint +0.1 … +1.2;
every value-aware policy completes a 64 GiB checkpoint in 1.5–1.9 s where the admit-all stream starves it to 15–75 s),
phases (+0.2 … +0.3); constructed phase-change / interleaved traces (+0.5 / −0.4; admit-all fails the SLO there at
14–35%); CONSTRUCTED stress: the joint rules fire only when the CXL path is cut to ≤ 6 GB/s (a load ~8×
beyond 70B 8×), and there a value-blind congestion drop (independent) beats the value-ordered one by 2–3 points; a
DRAM budget starved to 1 GB/s gives value placement +0.2 … +0.8. (5) *Decomposition (Task G):* the value signal
carries 97–100% of the gain and all of the write / interference reduction; the cost signal adds SLO safety to
admit-all only; plain second touch instead of the adaptive admission costs 7–9 points at 70B; without contention the
joint policy degenerates to the independent one by construction. (6) *Application level (Task F, replay):* recompute
−5 … −9%, TTFT model −8 … −9%, host writes −88 … −91%, DRAM writes −83 … −95%, p99 1.5–36% → 0.1–1.9% — all from RQ1;
joint vs independent 0.0 ± 0.3%.
**Decision.** Gate 3 (joint vs the best independent combination: recompute −10% or DRAM writes −30% at equal hits,
traceable to blocks decided differently) is **not met** — nothing is decided differently in any real-trace run. The
core hypothesis H2 is not supported on this hardware at single-host KV-cache scale; H1 (value has usable structure)
stands (RQ1). **Recommendation: do not implement the minimal unified manager on the current hypothesis.** The
defensible contribution the evidence supports is "value-aware admission makes DRAM/CXL KV caching interference-free
and makes cost-aware placement unnecessary at single-host scale" (RQ1 + RQ3), with the existing budget-gated split as
the (idle) safety mechanism — a smaller claim than the charter's C2, to be discussed with the user / advisor.
**What could still change the picture (unverified):** interference beyond 24 GB/s of DRAM writes (extrapolated);
CPU-copy emulation vs GPU DMA; DRAM capacity contention with the neighbour; loads whose filtered stream exceeds ~46
GB/s (≥ 40 servers of this trace at 70B, or far larger blocks); workloads whose reuse is not dominated by dead blocks;
checkpoint producers at a higher duty cycle; multi-tenant caches sharing one path.
**Correction recorded:** the "TB written (scored half)" columns of the three admission-study reports of 2026-10-20/21
count the whole trace (×2); relative reductions and hit shares are unaffected (details in the Phase 3 file).

## Update 2026-10-22 (Phase 3, hardware validation) — the filtered-write interference claim on the real machine (`docs/experiments/2026-10-21-hw-validation-filtered-writes.md`)
**Question:** the Phase 3 verdict rested on trace replay plus the interpolated interference curves. Do the SAME write
decisions, replayed as physical host-memory writes beside the real 80-thread Adam step, show what the model predicted?
**Method (HW, CPU replay):** the Phase 3 simulator re-run with a per-store write log (CSV rows identical, so the logs are
the Phase 3 decisions); a new replayer (`kvreplay.c`: non-temporal AVX2 stores from a pseudo-random source, 64 workers on
CCDs 6–7, 9.5 GB/s per-stream link pacing, 64 GiB arena, live token bucket) issues every DRAM-targeted store at its offer
time; the CXL-targeted stores are counted but NOT issued because `/dev/dax*` are root 0600 since the 2026-10-18 reboot
(blocker recorded; admin fix needed). Adam on cpus 0–79 as on 2026-10-12; SLO p99 during / quiet − 1 ≤ 7%; 3 repetitions
per cell, null runs, placement and store-primitive controls; 71 runs.
**Findings.** (1) The replayer reproduces the planned streams exactly (start delay p99 ≤ 0.2 ms, rates equal at 1 s /
100 ms / 10 ms). (2) Admit-all breaks the SLO at every configuration: p99 +8.3 … +9.0% (8B 8×), +14.1 … +15.7% (70B 4×),
+25% (70B 8×), medians +4.4 … +12.7%. (3) The RQ1-filtered stream stays inside it with margin: +1.6 … +2.8% at 8B 8× /
70B 4× and +4.0% at 70B 8× (medians ≤ 0.8%), repeatable to ±0.4 points, null runs −0.6 … 0.0. (4) The independent
budget-gated placement, decided live, redirects 9–29% of the DRAM candidates and trims the cost to +1.0 … +1.7% (+2.4%
at 70B 8×). (5) Model vs hardware: right in verdict and order; low by 0.2–1.2 points for the filtered stream (its 10-ms
bursts of 13–19 GB/s, 10× the mean, are outside a mean-rate curve), within −1.5 … +2.0 for admit-all inside the
calibrated range and high beyond it (36% predicted vs 25% measured at 70B 8×). (6) Conditions found: writer threads on
the victim's own CCD double the filtered cost (+5.4 … +6.5%, no margin; CPU sharing itself ≤ 2.4 points) and regular
read-for-ownership stores do the same (+6.1%); with DMA-like writes from another core group the numbers hold.
**Correction to the Phase 3 update above:** "0 budget refusals" was wrong — the Phase 3 CSVs show the bucket redirecting
15–35% of the DRAM candidates to CXL (indep vs value_split written blocks); drops and regime vetoes were 0 as stated. The
hit shares and write volumes already include the redirections; the phrase "the cost module never fires" means "the
congestion drop and the regime veto never fire" — the budget-gated placement acts, value-blind, in both the independent
and the joint policy.
**Decision.** The Phase 3 assessment stands, now with hardware support for its premise: after value-aware admission the
DRAM-side movement cost is small enough that nothing is left to trade off against value at these scales, and the

statement gains a measured form: reuse-aware admission turns a stream that breaks the neighbour's SLO by 1.2–3.6× into
one that fits it with margin on the real machine, and the budget-gated split keeps the residual bursts in check.
**Boundary to state with it:** CPU replay of the DRAM-targeted part (not GPU DMA, not the LMCache runtime); the CXL path
untested since the reboot; one victim (Adam); the placement and primitive conditions above.
