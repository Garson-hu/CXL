## Question
On healthy DRAM, does putting the stencil's write buffer (`new`) on CXL pay — when the
machine is idle, and when other tenants saturate DRAM's write path — and which read-back
policy is best?

## Setup (c28, 2026-09-14, after the 2026-09-09 reboot; one NUMA node, DRAM 97 GiB/s @4T)
- Stencil: 1-D leapfrog, three 8 GiB buffers; per step read old + cur (16 GiB), write new (8 GiB);
  16 compute threads pinned to cpus 0–15 (CCD0); 20 steps; steady state = steps 4–19.
- Case A: all three buffers in DRAM, pointer rotation.
- Case B: `new` on CXL = `/dev/dax1.0` (cards c1+e1, 2-way striped window, mmap), policies
  rotate / copyback / migrate / pingpong (pingpong's second device = `/dev/dax0.0`, the other
  window on the same two cards — dax2.0 is not accessible today). Copier threads (migrate,
  pingpong): 8 on cpus 32–39 (CCD2).
- Stores for `new`: normal (RFO + writeback) or NT (`--nt`).
- Worlds: **idle**; **pressure** = 80 NT-store writer threads (`membench stream-write-nt`,
  256 MiB per thread, node 0) on cpus 48–127 (CCD3–7), ~280 GiB/s, started 12 s before each
  pond run and killed after it (liveness checked at the end of every run). DRAM write path
  saturated; reader-side unaffected per 1b.
- 2 reps per cell; metric = median step time over steps 4–19, then median over reps.
- Invalid first attempt (`press-*.csv`): aggressor launched with 1 GiB/thread only 3 s before
  pond — its 80 GiB pre-touch overlapped most of the run, and the NT phase only reached steps
  16–19 (those steps show 2.7–3.05 s; the rest equal idle). Kept in the raw dir, not used.
  `verify-press-*.csv`: the two-config check that exposed this (A all-DRAM 2.60 s flat on all
  20 steps under a verified-live aggressor).

## Verdict
1. **Idle: `new` on CXL does not pay.** All-DRAM is fastest (0.261 / 0.213 s). Rotate costs
   +19%/+15% because one of three buffers is always CXL-resident; the copy-based policies cost
   1.5–2.2× because each step adds an 8 GiB CXL→DRAM copy that is not hidden (migrate's overlap
   recovers a third of it; pingpong's second device buys nothing when both windows are the
   same two cards). With healthy DRAM the "cheap DRAM reads vs expensive CXL reads" trade-off
   exists, and it favours DRAM — the opposite of the discarded 3b table.
2. **Under socket-wide DRAM write pressure, relocating the victim's writes is useless: the
   victim's DRAM READS are what starve** (1b: reads 12×, NT writes only −13–23%). Every
   policy that still reads DRAM runs 2.6–2.9 s (normal) / 1.7–1.9 s (NT) against 0.26 / 0.21
   idle. Placement of `new` becomes irrelevant to within ±10%.
3. **CXL is an isolation domain against DRAM drain mode.** The all-CXL stencil is unchanged
   under 280 GiB/s of DRAM writes (0.603 vs 0.599) — 4.3× faster than the all-DRAM stencil in
   that state, despite being 2.3× slower when idle.
4. **The direction the write tier must relocate is the aggressor's, not the victim's.** With
   the same write stream pointed at CXL (pair-saturated, 44 GiB/s), the all-DRAM stencil keeps
   95–100%. This is gate 2b (2026-08-25) at application scale.
5. What this means for Phase 4: the LULESH/VeloC and KV-cache experiments should measure the
   *co-runner's* protection (a DRAM-resident application next to checkpoint / KV-insert streams
   placed on DRAM vs CXL), with the stream's own cost as the secondary metric — not "does the
   app that owns the stream get faster".
