# 2026-10-07 — How much slower is a read from CXL than from DRAM, and what happens when reads and a checkpoint copy overlap?

**STATUS: CLOSED 2026-10-06 (measured in the evening).** Raw: `experimental_results/2026-10-07-read-cost/`
(`readcost.txt`, `gpuread.txt`, `ssd-read.txt`, `reuse-gaps.txt`, `machine-state.txt`). Tools: `benchmarks/memory/readcost.c`,
`benchmarks/memory/gpuread.c`. Part of the approved plan (read-cost table per reader type; reading while writing). Only the
two-card pair `/dev/dax0.0` is used (one card cannot be addressed alone; `dax2.0` is reserved).

## Setup
c28, idle machine. DRAM = anonymous memory with huge pages; CXL = `/dev/dax0.0` at offset 64 GiB (2 MiB pages). Single
dependent reads: one thread follows a random cycle of 64-byte lines through 1 GiB. Streaming: T threads read their own
256 MiB slices for 2 s, spread over four core groups (cpus 64.., 80.., 96.., 112..). Overlap: 4 streaming readers and one
chain reader while 8 threads (cpus 0–3, 16–19) copy pseudo-random data from DRAM into DRAM or into CXL with streaming stores.
GPU: RTX 4060 Ti (PCIe 4.0 x8), 1 GiB host-to-device copies from pinned DRAM and from the CUDA-registered CXL mapping.
SSD: 4 GiB file of random data, O_DIRECT reads. Three repetitions (GPU: ten); all repetitions agree within 1%.

## Results
| what | DRAM | CXL | CXL vs DRAM |
|---|---|---|---|
| one read that waits for the previous one | 134–136 ns | 224–227 ns | 1.67× slower |
| streaming read, 1 thread | 44.0 GiB/s | 24.4 GiB/s | 1.8× slower |
| streaming read, 2 / 4 / 8 / 16 threads | 86 / 165 / 258 / 279 GiB/s | 43.6 / 51.4 / 49.0 / 48.7 GiB/s | CXL tops out at ~51 GiB/s |
| GPU reading 1 GiB | 12.49 GiB/s | 12.48 GiB/s | the same (the GPU link is the limit) |
| for comparison: the SSD, O_DIRECT | — | — | 2.6 GiB/s one stream (4 MiB blocks), 2.9 GiB/s four streams |

Reading while a checkpoint copy runs (medians of 3):
| reader | copy | reader bandwidth (4 threads) | one dependent read | the copy's own rate |
|---|---|---|---|---|
| reads DRAM | none | 165.2 GiB/s | 134.6 ns | — |
| reads DRAM | into DRAM | 85.7 GiB/s (−48%) | 184.8 ns (+37%) | 88.7 GiB/s |
| reads DRAM | into CXL | 158.3 GiB/s (−4%) | 136.9 ns (+2%) | 43.9 GiB/s |
| reads CXL | none | 51.4 GiB/s | 228.6 ns | — |
| reads CXL | into DRAM | 51.4 GiB/s (0%) | 228.3 ns (0%) | 94.7 GiB/s |
| reads CXL | into CXL | 48.3 GiB/s (−6%) | 537.7 ns (2.4×) | 29.9 GiB/s (from 43.9) |

Second reuse of a key-value block (Mooncake traces, `reuse-gaps.txt`): the second reuse comes p50 138 / 126 / 111 s after the
first (conversation / tool agent / synthetic), p90 498 / 426 / 331 s. An LRU copy area of 80 GiB keeps a copied block
106 / 115 / 72 s at the promotion rates of the 2026-09-23 simulation and therefore catches 39 / 46 / 34% of second reuses;
160 GiB: 66 / 73 / 58%; 320 GiB: 85 / 93 / 86%.

## Verdict
- A processor reading CXL pays 1.7× per dependent read and 1.8× per thread for streaming; many threads together get at most
  ~51 GiB/s from the two cards, against ~280 GiB/s from DRAM. A GPU on this machine sees no difference at all.
- A checkpoint restored from CXL is read 8–17× faster than from this SSD (24–51 vs 2.6–2.9 GiB/s).
- Reads and a copy overlap well on CXL for bandwidth (−6%) but not for single dependent reads (2.4× longer); on DRAM the same
  copy costs readers half their bandwidth. The copy into CXL slows from 44 to 30 GiB/s while CXL is being read. This is the
  measured basis for the multi-tenant rule "hold bulk copies back while latency-sensitive reads use CXL" (DESIGN §10.12, rule 4).
- The DRAM copy area must cover the ~2-minute gap between reuses: 80 GiB catches about 40% of second reuses, 320 GiB about 90%.
